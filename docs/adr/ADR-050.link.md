# ADR-050 — Events binding-agnostic `topic`: `@DomainEvent.topic` gets a kernel sink on `EventTypeSpec` (link stub)

**Authoritative copy:** [`exeris-kernel/docs/adr/ADR-050-events-binding-agnostic-topic.md`](https://github.com/exeris-systems/exeris-kernel/blob/main/docs/adr/ADR-050-events-binding-agnostic-topic.md)

ADR-050 is a **cross-repo** decision owned by `exeris-kernel`. It gives the SDK's `@DomainEvent.topic`
a binding-agnostic kernel sink: an optional `String topic` on `EventTypeSpec` — the per-event-*type*
registration record, **not** the per-instance, primitive-only `EventDescriptor` (which stays
byte-for-byte unchanged, Valhalla-ready) — with `hasTopic()`, 3-arg factories, and blank-normalized-to-`null`
identity (blank ⇒ "no override", one identity with `null`, no spurious registry conflict). The Community Kafka
binding resolves `effectiveTopic = topicFor(hasTopic() ? topic() : name())` on **both** publish and
subscribe, so a topic-overridden type is never stranded; the in-memory `EventBus` stays topic-blind by
design (routes by event-type ordinal only — ADR-049 H2). Kernel v0.10.0 ships it (ACCEPTED 2026-07-01,
released 2026-07-02).

## Why this stub exists — the SDK is a named lockstep repo

ADR-050 §Engineering Protocol names the SDK by obligation: update the `@DomainEvent.topic`
"Open-Core status" javadoc from the old stance ("the Open-Core event engine does not route on it; the
generator preserves it as a source reference only") to the new one ("carried on the per-type
`EventTypeSpec`; broker bindings honour it; the in-memory bus treats it as advisory"). That stance
update is the SDK's whole lockstep slice — the design-time capture (`@DomainEvent.topic`, a required
`String`) and the AST carrier (`DomainEventMetadata.topic`) predate the ADR and needed no change.

## What the SDK owns vs. does not

| Piece | Owner | Status |

| `EventTypeSpec.topic` seam + Kafka `effectiveTopic` (publish + subscribe) + TCK | `exeris-kernel` | ✅ shipped in v0.10.0 |

## When to consult ADR-050 from the SDK

- Changing `@DomainEvent.topic` semantics (optionality, blank handling, placeholders) — the kernel
  normalizes blank → `null` ("no override"); the SDK surface must keep the same identity: a blank
  `topic` means "fall back to the binding's default routing", never a distinct routing target.
- Anything per-instance — deliberately out of ADR-050's scope. `topic` is a static per-*type*
  attribute; the per-instance routing knob is the separate `routingKey`, and a per-instance topic
  override would be a later additive kernel step, not an SDK-side reinterpretation.
- The other `@DomainEvent` messaging attributes (`exchange`, `routingKey`, `partitionKey`, `ttlMs`, …)
  — **not** covered; only `topic` has a kernel sink. They keep their existing (broker-tier) status.
