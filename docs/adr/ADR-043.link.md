# ADR-043 — SSE-first kernel HTTP streaming via a sibling `HttpStreamExchange` (link stub)

**Authoritative copy:** [`exeris-kernel/docs/adr/ADR-043-kernel-http-streaming-spi.md`](../../../exeris-kernel/docs/adr/ADR-043-kernel-http-streaming-spi.md)

ADR-043 is a **cross-repo** decision owned by `exeris-kernel`. It introduces a server-push HTTP
streaming primitive in `eu.exeris.kernel.spi.http` — a sibling `HttpStreamExchange` (the streaming
twin of the respond-once `HttpExchange`), an `@FunctionalInterface HttpStreamHandler`, an
implementation-blind `StreamEvent` record (SSE `event:`/`data:`/`id:`/`retry:`), and a typed
`HttpRouter.Builder.streamRoute(method, path, handler)` registration. Kernel `0.10.0-SNAPSHOT`
implements it (ACCEPTED 2026-06-21).

## Why this stub exists — the SDK is a named affected repo

ADR-043 §Context names the SDK by surface: the SDK **already advertises** streaming
(`@ExerisDomain(realTimeApi = true)`, `@Action(streaming = true, streamEventType = …, realTimeUpdates)`),
but those attributes were **inert** because no kernel primitive existed to bind to. Kernel 0.10 lands
that primitive, so the SDK → tooling streaming chain is now unblocked. The decision that fixes the
build-time *emitter shape* (processor↔generator contract + Java/TS parity) is a separate
**tooling-owned** ADR — see [RFC-2026-06-22 SSE Stream Emitter (tooling)](../../../exeris-tooling/docs/rfc/RFC-2026-06-22%20SSE%20Stream%20Emitter%20%28tooling%29.md).
This stub is the SDK-side awareness anchor, not the design.

## What the SDK owns vs. does not

The SDK's only obligation is the **additive AST surface** the per-action emitter consumes — it does
**not** co-own the emitter-shape decision (that is tooling's ADR), and a streaming AST widening does
**not** warrant its own SDK ADR (it is an additive wire-format change, same posture as the 0.7.0 saga
/ event-handler / projection growth, tracked in `ROADMAP.md`, not in the ADR registry).

| Driver | AST dependency | SDK status |
|---|---|---|
| **Entity-level** `@ExerisDomain(realTimeApi)` (tooling Slice 1) | `DomainMetadata.realTimeApi` | ✅ already plumbed end-to-end |
| **Per-action** `@Action(streaming)` (tooling Slice 2) | `ActionMetadata.streaming` / `streamEventType` / `realTimeUpdates` | ✅ added in 0.8.0 (schema `0.8.0`) — the cross-repo twin of the T1 ↔ `exeris-sdk` per-action dependency |

The build-time processor extraction and codegen consumption of these fields, plus the `-io` reader
parity, remain **`exeris-tooling`** work (coordinated, per ADR-042 reader↔processor parity).

## When to consult ADR-043 from the SDK

- Adding or reshaping the streaming AST fields on `ActionMetadata` / `DomainMetadata` — keep them the
  faithful AST twin of the `@Action` / `@ExerisDomain` attributes; the kernel SPI (`StreamEvent` wire
  fields) is the downstream contract the codegen targets, so do not encode transport detail
  (`text/event-stream`, chunk framing) into the AST — those are Core's, never the SDK's.
- A wire-format change to the streaming fields — it is a schema bump (see `SchemaVersion`), absorbed by
  the tooling processor + `-io` reader together.
