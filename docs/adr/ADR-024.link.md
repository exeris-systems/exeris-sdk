# ADR-024 — Capability Composition Model (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-024-capability-composition-model.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-024-capability-composition-model.md)

ADR-024 is the **ecosystem-owned** capability composition decision (authoritative in `exeris-docs`):
caps declare `@CapabilityModule` / `@Provides` / `@Requires` / `@CapabilityLifecycle` in pure source;
the build-time tooling resolves the `@Requires`→`@Provides` DAG, derives the lifecycle order, and
emits a stamped `cap-manifest.json` per composition (obligation 7); the SKU boot asserts the stamp
and conducts the four-phase cap lifecycle (obligations 8/8a/8a′/8b); the open kernel stays
**cap-blind** (obligation 9). Two amendments shape the SDK's runtime slice: the 2026-06-25
"Composition Runtime Placement" re-amendment (the runtime ships *in the SDK*, into each SKU
artifact — `exeris-platform` only consumes it) and the 2026-07-21 "Boot Conductor Call Site"
amendment (the conductor is invoked by the generated SKU bootstrap inside
`KernelBootstrap.boot(kernelMain)` after `KERNEL READY` — never registered as a kernel `Subsystem`;
the cap layer contributes no node to the kernel bootstrap DAG).

## Why this stub exists — the SDK realizes four ADR-024 obligations

The SDK is where most of ADR-024's cap-facing surface lives; each module maps to a named obligation:

| SDK piece | ADR-024 obligation | What it is |
|---|---|---|
| `eu.exeris.sdk.annotation.capability` (`@CapabilityModule` / `@Provides` / `@Requires` / `@CapabilityLifecycle`) | the annotation surface | SOURCE-retained markers, realized per [ADR-038](ADR-038-capability-annotation-surface.md) (the SDK-owned realization decision) |
| `exeris-sdk-composition-spec` | 8b | The one canonical `cap-manifest.json` read-schema (`CapManifest`, incl. the per-module-body `lifecycleOwner`) + content-binding algorithm (`CompositionBinding`), shared by the tooling emitter and the boot runtime |
| `exeris-sdk-composition-lifecycle` | 8a | The cap-facing four-phase hooks interface `CapabilityLifecycleHooks` (`initialize` / `ready` / `drain` / `terminate`) — zero dependencies by enforcer, so cap authors compile against annotations + this jar only |
| `exeris-sdk-composition-runtime` | 8/8a + 8a′ | `CompositionStampAssertion` (stamp presence / well-formedness / binding-match / version-match, fail-fast before any cap effect) + `CompositionConductor` (manifest-driven hook discovery, `initialize*`/`ready*` in verbatim `initOrder`, reverse `drain*`/`terminate*` under the composition-wide budget, `CompositionBootException` on failure) |

What the SDK does **not** own: DAG resolution / validation and manifest emission (build-time,
`exeris-tooling`); the deploy-time control plane (`exeris-platform`, obligation 8c); and any kernel
awareness of caps — nothing here lives in or is called from a kernel package (obligation 9).

## Engineering status

- **Conductor landed (SDK 0.9.0):** stamp assertion → reflective `lifecycleOwner` discovery →
  four-phase driving with fail-fast prefix unwind and the 30s-default drain budget. The manifest
  `lifecycleOwner` is consumer-modeled without a schema bump (cap-manifest `schemaVersion` stays 2;
  the field is not binding-covered).
- **Generated call site pending (tooling):** the SKU bootstrap that emits the conductor invocation
  ships with the `exeris-tooling` bootstrap emitter (gateway-caps plan, Phase 1/2); until then a
  hand-written SKU entrypoint invokes the conductor directly — the library contract is identical.

## When to consult ADR-024 from the SDK

- Changing the `cap-manifest.json` consumer schema or the content-binding canonical form — both are
  obligation-8b contract surfaces shared with the tooling emitter; a binding drift false-fails every
  deploy, and a schema change needs the `KNOWN_SCHEMA_VERSION` handshake bumped in lock-step.
- Changing `CapabilityLifecycleHooks` semantics (idempotent `initialize`, the all-caps `ready`
  barrier, drain-budget cooperation, re-entry-safe / non-throwing `terminate`) — these phase
  contracts are the ADR's, not the SDK's to reinterpret.
- Anything that would give the kernel a cap-facing seam or register the conductor as a kernel
  `Subsystem` — forbidden by obligation 9 and the 2026-07-21 amendment; the kernel stays cap-blind.
