# Exeris SDK — Roadmap to 1.0.0 GA

The SDK defines the **contract** between user domain code and Exeris tooling.
1.0.0 GA means: **the contract surface is frozen**. Downstream consumers
(`exeris-tooling`, `exeris-platform-lsp`, IDE plugins, future capabilities)
can pin to it with semver guarantees.

This file tracks scope per milestone. Items marked `[ ]` are open; `[x]` shipped.

---

## 0.2.0 — quality gates + pre-publish hygiene

> Goal: CI exists, contract is testable, POMs are publishable.

- [x] **CI** — `.github/workflows/build.yml` runs `mvn -B -ntp verify` (Java tests + JaCoCo 85% instruction/line gate on source-model) and `npm run test:coverage` for the ui-kit (Vitest with v8 coverage, 85% per-file thresholds). JaCoCo + Vitest reports uploaded as artifacts on every run.
- [x] **JaCoCo 85% gate on `exeris-sdk-source-model`** — `jacoco-maven-plugin` 0.8.14 (earlier versions don't support JDK 26 class file v70; baseline moved to v69 in 0.10.0, ADR-069); current measured coverage is 99.9% instructions / 100% lines / 94% branches across 50 classes. Annotations module is exempt from the gate (no executable code) but has `AnnotationContractTest` enforcing SOURCE retention + @Target across all top-level annotations via reflection — caught a real contract violation on first run (`SoftDeletedBy` was RUNTIME-retained, now fixed).
- [x] **JSON round-trip tests per AST record** — `AstJsonRoundTripTest` exercises every AST record (19 in total, including the three graph leaves directly) through Jackson 3 serialize → deserialize and asserts deep equality. Caught two real wire-format bugs on first run: (a) `ActionParamMetadata` was a class with record-style accessors that Jackson 3 didn't recognize as getters, dropping every field on serialization — fixed by migrating to a record (consistent with all other AST types); (b) Jackson 3 strict-mode rejects `null → primitive` coercion that Jackson 2 tolerated — `FAIL_ON_NULL_FOR_PRIMITIVES=false` requirement documented in `eu.exeris.sdk.sourcemodel.ast` package-info as a consumer contract. Known limitation: `@JsonInclude(NON_DEFAULT)` on `FieldMetadata` drops `Long(0)` because Jackson 3's NON_DEFAULT treats boxed-zero as "empty" — tracked under Field/Validation overlap fix
- [x] **JDK baseline rationale** in README, so teams on an LTS don't read the floor as an oversight. **Superseded in 0.10.0 ([ADR-069](docs/adr/ADR-069-jdk-baseline-lts.md)):** the original text explained why *26* was required, resting on the kernel being pinned there. Kernel ADR-066 measured that premise false and moved the distributable line to JDK 25 LTS, so the SDK followed — Virtual Threads and Panama FFM are real kernel requirements and are GA below 25, so they never fixed the floor at 26
- [x] **Field/Validation overlap fix** — picked canonical locations: `required` lives on `@Field` (it's a field-shape property, not a validation rule); `inCreate`/`inUpdate` stay on `@Field` (form-lifecycle scope). `@Validation.required` and `@Validation.validateOn` are now `@Deprecated(forRemoval = true)` with javadoc pointing at the canonical attributes — to be dropped in 1.0.0. Documented end-to-end in `eu.exeris.sdk.annotation` and `eu.exeris.sdk.sourcemodel.ast` package-info. Wider `min`/`max`/`pattern` overlap between `FieldMetadata` and `ValidationMetadata` is documented and deferred to the 0.6–0.9 cleanup phase, where budgetHQ usage will inform the right cut (landed 0.9.0 — ADR-054)
- [x] **Pre-publish POM metadata** — root POM now declares `<url>`, `<organization>`, `<licenses>`, `<developers>`, `<scm>`, `<issueManagement>`, `<distributionManagement>` (Sonatype Central Portal). Required by Maven Central; without these the publish step would fail validation
- [x] **Bump `jackson-annotations` `3.0-rc5` → `2.21`** — Jackson 3.x deliberately keeps annotations on the legacy 2.x line (per jackson-bom 3.x: `jackson.version.annotations=2.20+`). The 3.0-rc* annotations track was abandoned. Required for Jackson 3 databind 3.1.2 to load (`JsonSerializeAs` is a 2.21 addition)

## 0.5.0 — bidirectional sync surface

> Goal: SDK exposes the metadata mutations that LSP, Studio, and IDE plugins call. Design locked in [ADR-042](docs/adr/ADR-042-bidirectional-mutation-surface.md) (implements [RFC-2026-06-11](docs/rfc/RFC-2026-06-11-source-model-conflict-resolution.md)); records in `source-model`, detection + application in `-io`, baseline-trust fields stamped by the `exeris-tooling` annotation processor. **All four slices landed, both repos** — the milestone is closed end to end.

- [x] `MutationOp` records (add/rename/change-type field, change relationship cardinality, …) — `source-model`, path-addressed (ADR-042 slice 1). Sealed interface with nine nested op records (`AddField`/`RemoveField`/`RenameField`/`ChangeFieldType`/`AddRelationship`/`RemoveRelationship`/`ChangeRelationshipCardinality`/`AddAction`/`RemoveAction`); polymorphic JSON via an `"op"` discriminator. New package `eu.exeris.sdk.sourcemodel.mutation` (operations over the AST, not AST nodes); JavaParser-free, Jackson-only — zero-coupling enforcer green
- [x] `MutationResult` records — four outcomes: `SUCCESS` / `CONFLICT` / `VALIDATION_ERROR` / `NO_BASELINE` (ADR-042 slice 1). Sealed interface; `Conflict` carries baseline/current/intended values; `NoBaseline` shape frozen with a `NoBaselineCause` enum (`MISSING_BASELINE`/`STALE_DIGEST`/`SCHEMA_VERSION_SKEW`); `"outcome"` discriminator
- [x] Path-based addressing (`/entities/Order/fields/total`) — shared by ops and conflict reports. `MutationPath` (build/parse/validate + `isSameOrAncestorOf` for the slice-2 ancestor-or-descendant rule); ops carry the path as a plain wire string
- [x] AST-level three-way conflict detection in `-io` (ancestor-or-descendant overlap; convergent edits are `SUCCESS`) — ADR-042 slice 2. `SourceModelConflictDetector.detect(op, baseline, current)` compares `read(currentSource)` against the deserialized baseline at member granularity (field/relationship/action paths): drift = current ≠ baseline; conflict = drift ∧ non-convergent (the user hasn't already landed on the op's intent); sibling edits never conflict. Returns `SUCCESS`/`CONFLICT`, plus `VALIDATION_ERROR` for the structural rejections visible without a baseline (unparseable path, path-kind/op mismatch, wrong entity). Pure over two `DomainMetadata` values — no source reading, no digest, no `NO_BASELINE` (slice 3) and no mutation (slice 4). Hand-built SUCCESS/CONFLICT/convergent/sibling matrix + a budgetHQ corpus-backed case
- [x] Baseline-trust fields (ADR-042 slice 3, **cross-repo — both halves landed**). **SDK side:** `source-model` gains the shared contract — `SchemaVersion.CURRENT` (a dedicated wire-format-schema constant, decoupled from the Maven artifact version so a no-AST-change release doesn't read as a skew), `SourceDigest` (pure, JavaParser-free, line-ending/trailing-whitespace-neutral SHA-256 so both codegen and `-io` compute it identically), and `BaselineTrust` (the two trust fields as JSON siblings of the domain, each read blind to the other via `ignoreUnknown`). `-io` `SourceModelConflictDetector.checkBaselineTrust` + JSON/source `detect` overloads map missing/unparseable/schema-skew → `NO_BASELINE` before detection. **Decision:** per ADR obligation 4–5 tension, `STALE_DIGEST` is **not** a detection-time block — three-way detection runs on an edited source (its whole point); the digest is the apply-time optimistic-concurrency token (slice 4). **Tooling side landed:** `ExerisDomainProcessor.buildMetadataNode` stamps both fields as JSON *siblings* of the serialized `DomainMetadata` in `exeris-metadata/<entity>.json` — not a wrapper, so a plain `DomainMetadata` read still works and a `BaselineTrust` read of the same file picks up just these two. Two details worth keeping straight against the ADR text: the writer is the **annotation processor**, not codegen (the ADR says "codegen emits", which the implementation resolved to the processor, since that is where the source text is), and `schemaVersion` is read off `BaselineTrust.current()` at runtime rather than referenced as the `SchemaVersion.CURRENT` compile-time constant, so the processor cannot inline a stale value. `sourceDigest` is `SourceDigest.of` over the entity's raw source text via the javac Compiler Tree API; where that API is absent (some IDE/incremental environments) the digest is omitted and only `schemaVersion` is stamped, degrading to the slice-3 trust check without the slice-4 token rather than failing the build. `.link.md` stubs exist in both `exeris-tooling` and `exeris-platform`, and `exeris-platform-lsp` declares `exeris/applyMutation` (`ExerisProtocolExtensions:39`) with an `ApplyMutationParams` carrying `baselineJson` + a `concurrencyToken` — so the digest travels **both** ways by design: stamped into the baseline for the staleness check, and passed in the request as the apply-time token (ADR-042 obligation 5, "one mechanism, not two")
- [x] Conflict-aware application + optimistic concurrency token (ADR-042 slice 4). `SourceModelMutationApplier.apply(op, baselineJson, currentSource[, token])` composes detection (slices 2–3) with the idempotent writer: applies only on a `SUCCESS` verdict — never over a non-convergent user edit — and returns `ApplyResult{outcome, source}` (source returned unchanged on `CONFLICT`/`NO_BASELINE`/`VALIDATION_ERROR`; idempotent no-op when the op is convergent). The `sourceDigest` is the apply-time optimistic-concurrency token → `STALE_DIGEST` when the live source moved since the op was computed. `VALIDATION_ERROR` covers `changeRelationshipCardinality` (structural — no writer mutation behind it) and writer/parse rejections. Single-op; conflict-aware **batch** apply is deferred (it must thread the accumulating tooling edits through detection — own semantics)

### Annotation-surface honesty — inert attributes (issues to address)

> An internal surface review found attributes the SDK **advertises** but no consumer honours — they read as live configuration while silently doing nothing. Logged here as roadmap issues (not yet opened on GitHub). The SDK-owned obligation is the same in every case — **make the annotation tell the truth**: wire it end-to-end, or run the deprecation pipeline so it stops reading as configuration. Some pair with a downstream gap (a tooling consumer or a kernel SPI) tracked in `exeris-tooling` / `exeris-kernel`.

- [x] **`@ExerisDomain` system-field overrides are inert** — all nine override attributes (`tenantIdField`, `versionField`, `softDeleteField`, `softDeleteTimestampField`, `softDeletedByField`, `createdAtField`, `createdByField`, `updatedAtField`, `updatedByField`) are advertised, but the repository generator hard-codes the canonical accessor names. Decide: honour them in tooling, or deprecate + document the canonical names (`tenantId`/`version`/`createdAt`/`createdBy`/`updatedAt`/`updatedBy`/…) as mandatory in `MIGRATION.md`. **Resolved (honoured in tooling, T5/T6):** the processor extracts the overrides into `SystemFieldsMetadata` and the repository + Flyway generators resolve each logical field through it (`KernelRepositoryGenerator`, `KernelFlywayGenerator`), falling back to the canonical accessor only when an override is unset — the attributes are live, not inert.
- [x] **`@Relationship.targetEntity` is inert** — the processor derives the target from the field's Java type, so the attribute does nothing on the explicit-UUID-FK style. Decide: document the entity-typed requirement, or push tooling to prefer `targetEntity` when set (fall back to the field type only when `void.class`). **Resolved (honoured in tooling, T4):** the processor now prefers `targetEntity` when set and falls back to the field type only when unset.
- [x] **`@Action(name=…)` is inert** — action identity is the method name, so a `name` chosen to dodge a bean-setter collision has no effect, even though `name` is a *required* attribute. Decide: clarify in the javadoc that the method name is the identity today, or make tooling honour `name` as the stable action id. **Resolved (honoured in tooling, T3):** the processor reads `name` as the action identity and it flows through to the emitted action path/id.
- [x] **`@DomainEvent.topic` is inert against the Open-Core event bus** — topic routing is an enterprise/Kafka-tier concern. Javadoc note that `topic` is enterprise-tier routing metadata, ignored by the Open-Core event engine. **Resolved (javadoc-honesty):** `@DomainEvent.topic` carried an Open-Core-status note — the Open-Core event engine does not route on it (the generator preserves it as a source reference only); it gains meaning under the enterprise/Kafka messaging tier. **Superseded (kernel v0.10.0, ADR-050 — see `docs/adr/ADR-050.link.md`):** `topic` now has a binding-agnostic kernel sink — an optional `EventTypeSpec.topic` on the per-*type* registration record (blank ⇒ "no override"), honoured by the **Community Kafka binding on both publish and subscribe** (`effectiveTopic` = override, else type name; `topicPrefix` still applies) — so topic routing is live in Open-Core under a broker binding, no longer enterprise-tier-only; the in-memory `EventBus` stays topic-blind by design (ADR-049 H2). The `@DomainEvent.topic` javadoc stance is updated to match — the SDK's ADR-050 lockstep obligation, done. **Tooling lockstep landed too (exeris-tooling #132, verified on main 2026-07-02):** the `KernelEventGenerator` now populates `EventTypeSpec.ofPersistent(name, ordinal, topic)` from the declared topic (blank ⇒ 2-arg factory, "no override") — the `@DomainEvent.topic` → AST → generator → `EventTypeSpec` → Kafka `effectiveTopic` chain is live end-to-end; the in-memory bus keeps it advisory.
- [x] **Capability surface is inert end-to-end** — `@Provides` / `@Requires` / `@CapabilityModule` (+ their AST records) are read into the AST (0.4.0 Slice 3) but no processor extraction nor codegen consumer uses them. Decide: wire the graph end-to-end with a tooling registry consumer, or a javadoc + `MIGRATION.md` note that the capability annotations are reserved and not yet consumed in Open-Core. **Resolved (SDK side — javadoc-honesty):** the `capability` package-info now carries an "Open-Core status — reserved, not yet consumed" note (declared shape + `-io` reader exist, but no processor extraction / codegen consumer yet, so declaring them has no generated effect). Wiring the cap graph end-to-end remains `exeris-tooling` work. **Superseded (0.8.0/0.9.0 — consumed end-to-end):** the tooling processor extracts the capability annotations, `VerifyCapabilitiesMojo` + `CapabilityGraph` validate the dependency DAG, the stamped `cap-manifest.json` is emitted, and the 0.9.0 boot conductor drives the four-phase lifecycle from it — the capability package-info now carries the live "extracted and conducted" status. The remaining not-yet piece is the tooling-generated SKU bootstrap call site (gateway-caps plan).
- [~] **Streaming / real-time attributes are inert** — `@ExerisDomain(realTimeApi=true)` and `@Action(streaming=true, streamEventType=…, realTimeUpdates=true)` advertise server-push, but there is no Open-Core streaming HTTP SPI to back them (kernel-owned root cause). Javadoc note that they are not wired in Open-Core until the kernel streaming affordance lands; the annotations gain meaning once it does. **Resolved (javadoc-honesty):** all four attributes (`@ExerisDomain.realTimeApi`, `@Action.streaming` / `streamEventType` / `realTimeUpdates`) carry an Open-Core-status note that they are inert until the kernel streaming HTTP affordance lands. **Unblocked (kernel v0.10.0 — shipped 2026-07-02; ADR-043 ACCEPTED 2026-06-21):** the kernel streaming HTTP SPI (`HttpStreamHandler` / `HttpStreamExchange` / `StreamEvent` / `HttpRouter.streamRoute`) landed, so the SDK → tooling streaming chain is unblocked; the emitter shape is fixed in [RFC-2026-06-22 (tooling)](https://github.com/exeris-systems/exeris-tooling/blob/main/docs/rfc/RFC-2026-06-22%20SSE%20Stream%20Emitter%20%28tooling%29.md) — see `docs/adr/ADR-043.link.md`. ### AST expressiveness — behaviour, choreography, topology (modeling gaps)

> Exercising the SDK against a non-trivial generated domain (well beyond the CRUD-shaped corpus) surfaced a class of gaps distinct from the inert-attribute fixes above. The AST models **structure** richly — entities, fields, actions, events, and sagas-as-an-ordered-list — but models **behaviour** (what a step or handler *does*), **choreography** (which event drives which reaction), and **topology** (which service exposes what) thinly. The consequence is that a generated app's *scaffolds* are real but their *bodies* are hand-written, because the AST can't describe what a design-time tool (LSP / Studio) would draw. The SDK-owned obligation here is the same in each case: **grow the AST/annotation surface to express it**; the matching generation is `exeris-tooling`. The topology half is partly already covered — the capability annotations (0.4.0) carry the provide/require graph — so what remains SDK-side below is mostly behaviour + choreography. RFC-worthy in aggregate (each is a sizeable additive surface); list-only for now, no GitHub issues yet.

- [~] **Saga step semantics + typed transitions.** `SagaStepMetadata` is already a rich step descriptor — `order`, `service`/`command`, `compensation`, `timeout`/`maxRetries`/`retryBackoff`, `parallel`, `required`, `condition`/`skipOnConditionFalse`, `dependsOn` (a partial DAG), `producesEvents`, `inputMapping`/`outputMapping`, `errorHandler`. Two things are still missing: a step *kind* (await-timer / await-event / invoke / compensate — today the kind is only implied by which of `service`/`command`/`compensation` is set) and **typed transitions** as first-class edges (success → next, failure → compensate, timeout → retry; loops). `dependsOn` orders steps but doesn't carry the *outcome* an edge fires on, so a branch the consumer must encode by hand (via the returned outcome) can't be drawn or generated. Model step `kind` + a typed-transition shape (`@SagaTransition(from, to, on = SUCCESS | FAILURE | TIMEOUT)` or equivalent) so the await/dispatch/compensate body becomes generable; emission is tooling. Promotes the step list + `dependsOn` DAG into an outcome-edged state-machine graph. **SDK side done (0.7.0):** `SagaStepMetadata` grew `kind` (`StepKind` = INVOKE / COMPENSATE / AWAIT_EVENT / AWAIT_TIMER) + `effectiveKind()` (infers INVOKE/COMPENSATE from structure; await kinds need the explicit field), and `SagaMetadata` grew `transitions` (a `SagaTransition` edge list = `from` → `to` `on` a `TransitionOutcome` of SUCCESS/FAILURE/TIMEOUT/COMPENSATED, optional SpEL `guard`, null/blank `to` = terminal), with `hasTransitions`, factories (`success`/`failure`/`timeout`/`ofOutcome`), compact-constructor normalization (null-list → empty, default outcome SUCCESS, blank guard → null, blank `to` → null, `from` required non-blank) and defensive copy. Round-trip + focused-test coverage added; AST-owned enums (no annotation mirror, zero-coupling); schema stays `0.7.0` (same release as the ProjectionMetadata growth). **Annotation half done (0.9.0, shipped reserved):** `@SagaTransition` / `@SagaTransitions` (repeatable, saga-class-level: `from`/`to`/`on`/SpEL `guard`, blank `to` = terminal edge) + `@SagaStep.kind` (`UNSPECIFIED` default = absent AST kind, deferring to `effectiveKind()` inference), with annotation-side `TransitionOutcome`/`StepKind` enum mirrors of the AST-owned types (zero-coupling, the `ComponentType` precedent) and `@Derived`-style reserved-honesty notes. **Remaining (cross-repo, coordinated):** the `exeris-tooling` processor extraction into the grown record, with the `-io` reader extracting them in parity; a codegen consumer then turns the graph into the await/dispatch/compensate body. The operational `@SagaStep` surface (circuit breaker, idempotency, instance selection, per-step monitoring) stays deferred (additive).
- [~] **Event reactions / choreography — the missing AST record.** The `@EventHandler` annotation already exists (`@Retention(SOURCE)`, `@Target({METHOD, TYPE})`, with event-selection, `condition`, `priority`/`ordering`, transaction/retry, and saga-trigger attributes), but there was **no `EventHandlerMetadata` AST record** — so the processor could read a `@EventHandler` and had nowhere to put it, and the AST/codegen never saw the choreography backbone. `@DomainEvent` models the *emission* side; the *reaction* side was invisible to the AST. **SDK side done:** `EventHandlerMetadata` added (record + builder + `simple` factory + `isSagaHandler`/`hasCondition` convenience; blank→null / null-list→empty normalization in the compact constructor), wired into `DomainMetadata.eventHandlers` (additive, by-name JSON; old baselines read back an empty list), with `AstJsonRoundTripTest` (projection + saga shapes) and a focused `EventHandlerMetadataTest`. It captures the behaviourally meaningful facets; the operational attributes (`emitMetrics`/`logLevel`/`alertOnFailure`), nested `@RetryPolicy`, and `versions` are deliberately deferred (additive). Enum-valued attributes are stored as source-written strings (zero-coupling, as the capability records do). **Remaining (cross-repo, coordinated):** the `exeris-tooling` processor extracts `@EventHandler` into the record and a codegen consumer turns it into the reaction (emit-command | mutate | invoke), with the `-io` reader extracting it in parity. Related and still open: `@DomainEvent(trigger = STATE_TRANSITION, stateTransition = …)` is declarative-only — the AST names "fire when field X changes" but nothing models the old/new diff end-to-end (detection emission is tooling).
- [~] **`@Projection` AST record is too thin.** Both `@Projection` (a full annotation — event subscription, read-model config, partitioning, rebuild/consistency, caching, REST/GraphQL exposure) and `ProjectionMetadata` (wired into `DomainMetadata.projections`) already exist — but the AST record carries only `name` / `description` / `fields` / `cacheable`. It has **no source-aggregate link and no field-subset framing**, so the "expose this subset of *this* aggregate as a read-only view" pattern — the public-projection-vs-private-state split that pairs with the `universe` data-scope item above — can't be expressed even though the annotation can. SDK obligation: grow `ProjectionMetadata` (source aggregate + exposed-field framing, bridging the annotation's event-subscription model), not add a new annotation; generating the DTO + mapping is tooling. **SDK side done (0.7.0):** `ProjectionMetadata` grew the source linkage (`aggregateTypes`), event subscription (`events` / `eventClassNames` / `topicPattern`), and read-model identity (`model` / `schema`) alongside the existing `fields` subset; added `builder` + `of(name, aggregateType, fields)` factory + `hasSourceAggregate` / `hasFields`, with blank→null / null-list→empty normalization, `AstJsonRoundTripTest` (full + minimal shapes) and a focused `ProjectionMetadataTest`. Class-valued attributes stored as source-written strings (zero-coupling). The operational surface (partitioning / rebuild / consistency / monitoring / query API) is deferred (additive). **Remaining (cross-repo, coordinated):** the `exeris-tooling` processor extracts `@Projection` into the grown record and a codegen consumer emits the read-model DTO + mapping, with the `-io` reader extracting it in parity.
- [~] **Declarative-behaviour layer (`@Derived` / `@Rule`).** The deepest pattern behind the above: the SDK models structure, so the pipeline emits scaffolds and *all* behaviour is hand-written code the AST never sees. A slice of that behaviour is mechanical — derived fields, roll-ups, simple guards/formulas — and could be modeled declaratively (`@Derived(expression = …)`, `@Rule(…)`) rather than written by hand, leaving genuinely-complex domain logic as a marked escape hatch (a design-time tool must always keep one). RFC-worthy (large new surface); informed by ready Capabilities + SKU workloads — the same "let real usage inform the cut" discipline as the Field/Validation overlap, not budgetHQ. Server-side `@Validation` generation and full `@UI` fidelity are the smaller, known instances of the same "modelled but not generated" gap (their SDK halves already exist; the generation is tooling). **Direction set in [RFC-2026-06-18](docs/rfc/RFC-2026-06-18-declarative-behaviour-layer.md) (ACCEPTED):** the framed surface (opaque-`String` expression + `language` tag defaulting to `"spel"`; opt-in escape hatch; `@Derived` as a `FieldMetadata` facet, `@Rule` + top-level `@Rules` container as a `DomainMetadata.rules` list; `dependsOn` allows related-entity paths). The build trigger is **met** — an internal adopter exercising the SDK against a non-trivial generated domain has a concrete recurring need (roll-ups incl. cross-aggregate, discriminant→value maps, ratio/threshold guards, decay formulas). **SDK side done:** `@Derived` / `@Rule` / `@Rules` annotations in `exeris-sdk-annotations` (slice 1) + `DerivedMetadata` / `RuleMetadata` AST records (slice 2 — `FieldMetadata.derived` facet + `DomainMetadata.rules` list, `effectiveLanguage`/`effectiveSeverity` defaults, blank→null normalization, round-trip + focused tests), shipped reserved with a capability-style "generation pending tooling" honesty note; shares the `"0.7.0"` schema. **Remaining (cross-repo, coordinated):** the `exeris-tooling` processor extracts `@Derived` / `@Rule` into the records and a codegen consumer emits the derivation / constraint, with the `-io` reader extracting them in parity. A reaction/choreography sibling (`@Reaction`-shaped) is out of scope (overlaps `EventHandlerMetadata` + the `STATE_TRANSITION` gap).

### Annotation-surface honesty — 2026-08 evidence survey (new findings)

> A second, evidence-first pass traced **every** annotation attribute the whole way — annotation → processor / `-io` reader → generator → emitted artifact — against the `exeris-tooling` working tree (`9c72a8f`). It found cases the 0.9.0 sweep structurally could not, because that sweep enumerated attributes that are **not extracted**: anything extracted and then dropped at the far end of the chain passed it clean. Same SDK-owned obligation as the list above (make the annotation tell the truth), plus one obligation on the sweep method itself. Javadoc honesty notes land with the survey PR; the tracking dispositions are here.

- [x] **`@ExerisDomain.graphqlApi` is inert end-to-end — and it shows how the 0.9.0 sweep missed a whole class.** It *is* extracted (`ExerisDomainProcessor:981-983`), *is* carried on `DomainMetadata.graphqlApi`, and *is* declared in the TS wire schema (`exeris-codegen-ts/src/models/domain-model.ts:292`) — and then **no generator emits GraphQL anywhere**: no schema, no resolver, no endpoint, in either pipeline. `graphqlApi = false` suppresses nothing either, because there is nothing to suppress. It survived the 0.9.0 sweep because it dies at the **end** of the chain, not the start — the sweep's search key was "unextracted", and this attribute is extracted. **Method fix for the next sweep: trace to the emitted artifact, never to the AST.** Same shape, same miss: **`@Action.path` is a REQUIRED attribute with no AST component at all** (`ActionMetadata` declares no `path`) — routes derive from `@Action.name`, so every author is obliged to write a value that reaches nobody. **Resolved (javadoc-honesty, this PR);** wiring-or-removal for both goes to the 1.0.0 public-API surface review (`MIGRATION-0.x-to-1.0.md` §4).
- [x] **Repeating `@SagaStep` compiles and is then silently dropped by *both* readers — worse than inert.** The 0.9.0 fix made the `@SagaSteps` container `public`, so repeated `@SagaStep` now *compiles* from an external package; it did not make it *read*. The processor's `findAnnotation` matches an exact FQN and never sees the javac-synthesized `@SagaSteps` mirror; the `-io` reader takes `getAnnotationByName("SagaStep")`, which returns only the first match (`SourceModelReader:753-759`). Net: a method carrying two `@SagaStep`s emits **zero** steps, on a clean compile, with no diagnostic at any strictness. This is the one case in the survey where the compiler actively signals success over a silent loss. **Resolved SDK-side (javadoc-honesty, 0.10.0)** — the `@SagaSteps` javadoc claimed hand-written containers "read identically"; they do not, and it now states both readers' actual behaviour (processor: no step from that method; `-io`: the first one only) and tells the author to declare each step on its own method meanwhile. Container handling in both readers is a coordinated ADR-042 flip, cross-repo and unscheduled; `@DomainEvent` is the only annotation whose repeatable container *is* handled today and is the reference shape for that flip.
- [x] **`@GraphEdges` was package-private — `@GraphEdge` could not be repeated outside the SDK's own package.** A top-level type in `GraphEdge.java` declared without `public`, so every external repeated use failed to compile: "error: `GraphEdges.value()` is defined in an inaccessible class or interface" (confirmed by compiling from an external package, not inferred). This is the *identical* defect fixed for `@SagaSteps` in 0.9.0, and it was recorded in no CHANGELOG, ROADMAP or MIGRATION entry — the 0.9.0 fix treated one symptom rather than the class. **Fixed (0.10.0):** the container is `public`, extracted into its own `GraphEdges.java` per the `SagaSteps` precedent — same FQN, no wire or AST change (containers are flattened on extraction), and it was already in the `annotation-surface.txt` snapshot, so the surface guard needed no re-baseline. Verified the same way the defect was: the external-package probe fails to compile against the package-private class with the exact error above, and compiles against the public one. Every other repeatable container in the SDK is nested inside a public `@interface` and is therefore implicitly public, so these two top-level ones were the whole class and it is now empty. **Guard landed with the fix:** `AnnotationContractTest.repeatableContainersArePublic` reads the container off each `@Repeatable` (not off the package walk, which skips nested types — a nested container must stay covered) and asserts `Modifier.isPublic`; verified non-vacuous by reverting `GraphEdges` to package-private, which fails it by name. Fixing the symptom without the guard is what 0.9.0 did, and is why this recurred.
- [x] **`@Saga.version` is declared-but-unextracted, and the kernel just made it load-bearing (kernel ADR-064).** Same shape as the survey items above, found by re-reading the annotation against kernel v0.11 rather than by the survey's own sweep. The kernel now keys its plan catalog by `(name, version)`: v2 no longer evicts v1, a parked saga resumes on the exact version it parked under, an unregistered version **fails closed** instead of rebinding to the newest plan, and crossing versions needs a migration transform the application registers. The SDK attribute that would express that intent reaches no AST — the processor's saga extraction takes `name` / `description` / `timeout` / `maxRetries` only (`ExerisDomainProcessor:1745-1755`) and the `-io` reader mirrors exactly that set (`SourceModelReader:733-744`). `SagaMetadata.version` exists but holds the builder default `1` on every run, so `version = 3` produces an AST that says `1`, silently. Both producers are blind identically, so this is a hole in both rather than an ADR-042 divergence. **Resolved SDK-side (javadoc-honesty, 0.10.0):** the attribute now carries the kernel contract, the deployment consequence of bumping (or not bumping) it, and the not-extracted status. Extraction + transcription onto `FlowDefinition`, and where a migration transform is declared, are `exeris-tooling` slices against a preview-tier SPI — **1.x, not before**, same ordering argument as ADR-061
- [x] **`@ExerisDomain.roles` has no destination even after ADR-061 — the 0.10.0 note was one step too generous (kernel ADR-063).** The note added in 0.10.0 said route authorization was "the first surface these attributes could actually generate into", for both `roles` and `permissions`. Only half holds: `RouteRequirement` declares no role kind and decides through `PrincipalContext.hasScope` alone, and ADR-063 (owned by `exeris-spring-runtime`) deliberately keeps `hasRole(...)` out of the edge DSL rather than inventing a `ROLE_x`→scope convention, because that would stand up a second, silently-diverging authority model at the edge. Roles resolve at the *method* level via `@RequiresRole` against a build-time `methodId` the kernel cannot derive from a URL — the same `@Retention(SOURCE)` argument ADR-061 uses to hand the URL→policy table to `exeris-tooling`. **Resolved (javadoc-honesty, 0.10.0):** `permissions` is named as the half with a destination (named scopes); `roles` says plainly that what it would compile into, if anything, is undecided
- [ ] **`@CapabilityLifecycle` "may be a distinct class" — needs a decision, not a fix.** True for the `-io` reader (it takes the first non-interface class in the compilation unit carrying the annotation, with a passing test at `SourceModelIoTest:254-301`) and false for the processor (`lifecycleOwner` is set only when the `@CapabilityModule` class itself carries it, else `null`; the annotation is not in `@SupportedAnnotationTypes`, so a standalone annotated class is never visited — the processor's own comment explains why: a separate owner class would need an SDK-side identity attribute that does not exist). **The two AST producers therefore yield different `lifecycleOwner` values for identical source** — an ADR-042 parity break, not a doc bug: a round-trip through `-io` is not processor-equivalent for this attribute. Which side is canonical is unresolved; no ADR-024 amendment text exists in this repo either way. Related and equally unverified: the javadoc's "more than one `@CapabilityLifecycle` per capability is a build error the tooling validator rejects" — no cardinality check was found anywhere, and given the above the processor structurally cannot see a second one. **Decide before the freeze** — the answer is potentially surface (an SDK-side identity attribute) rather than only wording.
- [ ] **`-Aexeris.strict` cannot audit almost any of the reserved surface.** `INERT_ATTRIBUTES` has exactly two entries (both on `@ActionParam`) and `INERT_ANNOTATIONS` exactly one (`@EventSourced`) — and by the registry's own doctrine an entry requires the attribute to be *extracted but unread*, so it **structurally cannot flag anything that is never extracted**, which is what nearly all of the ~900 reserved attributes are. A user who sets any of them gets no warning at any strictness: the compiler is silent, and so is the processor. The registries are honest about what they cover; the limitation is that the honesty tooling's reach is a fraction of a percent of the declared surface, which is worth knowing before citing it as coverage. Even inside its own criteria it under-lists — `@ExerisDomain`'s AST-only attributes (`module`, `aggregate`, `restApi`, `graphqlApi`, `sensitive`, the three `cache*`, `fullTextSearch`, `searchConfig`, `internalClient`) all qualify and none is registered. Widening the registries is `exeris-tooling` work; the SDK-side lever is javadoc, which is why the honesty notes carry the load.
- [ ] **Cross-repo (`exeris-tooling`) — `@ActionParam.label` is read under a key that does not exist.** `ExerisDomainProcessor:1405` reads `getString(values, "displayName", null)`; `@ActionParam` declares `label()`, and the value map is keyed by the annotation element's simple name, so the read can never match and `ActionParamMetadata.displayName` is `null` on every processor run. `effectiveDisplayName()`'s fallback to `name` masks the drop completely, no test covers it, and `INERT_ATTRIBUTES` does not list `label` — which under the registry's own discipline reads as "`label` is consumed", when it is not even extracted. Exactly the `relationshipType` shape above (annotation key vs AST key), in the same file, fixed there and left here; the `-io` reader maps `label` → `displayName` correctly, so it is also a live P/R divergence. **Belongs to `exeris-tooling` — deliberately not opened as an SDK issue:** the SDK surface is correct as declared.
- [ ] **Cross-repo (`exeris-platform`) — the SDK asserts a platform port is superseded that the platform still ships.** `CompositionBinding` and `composition-runtime/package-info` state that collapsing to one canonical implementation removed the byte-verbatim platform port (ADR-024 8b); `exeris-platform/exeris-platform-composition-runtime/` still contains its own `CapManifest` / `CompositionBinding` / `CompositionStampAssertion`, is still a reactor module (`exeris-platform/pom.xml:75`), and its package-info still calls the algorithm "a verbatim port". Whether it is still *consumed* or is dead code awaiting deletion is unknown from this side. The disagreement cannot be closed from here — either the platform module goes, or the SDK claim narrows to what it can actually assert (one canonical implementation *in the SDK*). **Resolve in `exeris-platform`.**

### Kernel 0.11 SPI — dispositioned, reserved rather than deferred (amended by ADR-072)

> Kernel 0.11 adds two net-new SPI packages, and has since added two further
> additive contracts (ADR-061, ADR-062) that reach the SDK differently — one
> gives an existing inert attribute a destination, the other tightens what an
> existing attribute means. The kernel's own v0.11 plan labels
> them **preview-tier, post-1.0** surface ("none of them may creep into
> 1.0-blocking status"), and its `docs/stability-matrix.md` holds
> `…spi.scheduling` and `…spi.storage.blob` at tier `preview` since 0.11.0.
> Freezing an SDK annotation against a preview SPI would invert the stability
> ordering — the SDK's 1.0 promise is stronger than the surface it would be
> encoding. Both are net-new annotations + net-new AST records, i.e. additive
> and legal in a 1.x minor, **conditional on the record-growth stance above**.
>
> **Amended 2026-08-18 (ADR-072).** The two blob/job items below now ship in
> 0.11.0 rather than waiting for 1.x — *reserved*, and explicitly outside the
> 1.0.0 freeze, so the ordering argument above is honoured rather than
> overturned. The reservation meets the three-part test ADR-072 adopts as the
> standing rule: the enforcing kernel binding demonstrably exists (both packages
> shipped with their TCKs), the remaining gap is one named downstream slice, and
> both the annotation and the AST component say so. Promotion into the frozen
> surface is conditional on the kernel moving each package to `stable` **and**
> the `exeris-tooling` transcription existing. The other four items below are
> unchanged — none of them meets that test today.

- [x] **Blob storage (kernel ADR-056)** — `BlobStore` / `BlobRef` / upload+download handles with `StorageContext.isolationKey` scoping. Entity-First gap: there is no way to declare "this entity has an attachment" — `@Field.dataType` is a free-form String hint, and the ui-kit's `.exeris-file` class is presentation-only. Cron is the standard **five-field** syntax and nothing more, and the kernel's fourth (event-driven) kind is excluded there and therefore here — the SDK must not widen at the declaration site what the kernel narrowed at the execution site. The AST collapses the three mutually exclusive attributes into one `TriggerKind` discriminator, so a cron-*and*-interval combination the annotation forbids only in prose is unrepresentable downstream; both new records are class-level `NON_NULL`, the posture every small facet record in the package already uses — *not*, as this milestone initially reasoned, to dodge an ordinal-0 drop, which measurement showed does not happen (see the corrected DataScope note above). **Open, and one of the reasons this ships reserved:** a declaratively-scheduled action has no submitter, so there is no `PrincipalContext` to capture, and the kernel correctly fails a context-less job closed rather than running it under an ambient identity (ADR-057 obligation 5). The two available answers are a kernel-side service principal for declared jobs, or an SDK attribute naming a run-as identity — the latter puts an authorization decision in a design-time annotation and is the worse one on its face. Not the SDK's to settle alone; tracked in ADR-072
- [ ] **Graph heterogeneous multi-hop traversal** — kernel dispositioned this **post-1.0** in its own ROADMAP, narrowly: graph the subsystem stays in 1.0, but *this contract widening* is new surface the 1.0 ruling never assessed. `@GraphQuery` must not chase it ahead of the kernel
- [ ] **Flow await** — kernel dispositioned **1.0-recommended**, RFC-first: what "completion" means for a durable, parkable, cross-restart flow is the actual open question. No SDK shape to encode until that RFC settles; `@Saga` / `@SagaStep` stay as they are
- [x] **Route authorization (kernel ADR-061)** — the kernel replaced its hardcoded `/secure` convention with a declarable, path-shaped policy behind an `Optional` slot on `HttpKernelProviders`. The kernel cannot reconstruct a `methodId` at runtime — it is a `@Retention(SOURCE)` artefact — so the URL→policy table is explicitly `exeris-tooling`'s to emit, from the SDK's declarations. Honesty notes added on `roles` / `permissions` (0.10.0, the streaming-note pattern).

  ~~SDK work when it comes is extraction + AST carrier, not a new annotation; **1.x, not before**.~~ **Corrected 2026-08-28, and the correction is the whole of the 0.12.0 slice.** That sentence was wrong on its central claim, in the same shape as the `roles` correction two bullets up: extraction alone could not have produced the statement, because **the surface cannot make it**. Nothing in this SDK says *"this route is public."* `@ExerisDomain.roles` / `permissions` and `@Action.roles` / `permissions` are the only security-shaped attributes, and an empty value on any of them already means "nothing declared" — `@Action.roles` has documented empty as "accessible to all authenticated users" since 0.1.0 (`Action.java:241`), so the empty case could not be overloaded without colliding with a published meaning. A processor extracting all four would still emit a table with no way to express a permit-all route.

  **What made the gap load-bearing rather than theoretical.** `exeris-tooling` measured the cost of a naive fail-closed default and found two facts: an emitted application wires no identity at all, so `AUTHENTICATED` everywhere is 401 on everything; and one `HttpRoutePolicy` governs *every* path, so a fail-closed unmatched answer also closes hand-written consumer routes, health and docs. Both are documented consequences of the kernel contract, not defects — `HttpRoutePolicy.unmatched()` states them, and deliberately declines to exempt anything driver-side ("a driver-local notion of 'public' would be a second answer to the question this contract now owns"). The resulting shape — fail-closed for emitted routes, delegate the rest — makes a *generated* route fail closed, and a public one then has to be declarable or it becomes unbuildable.

  **Landed reserved in 0.12.0:** `@RouteAccess(PUBLIC | AUTHENTICATED)`, `@Target({TYPE, METHOD})`, with `DomainMetadata.routeAccess` / `ActionMetadata.routeAccess` carrying it. Meets ADR-072's three-part test — `HttpRoutePolicy` / `RouteRequirement` shipped with `AbstractHttpRoutePolicyTck`, the remaining gap is the one named `exeris-tooling` slice, and both the annotation and the components say so — so it ships **outside the 1.0.0 freeze**, on exactly the terms `@Blob` / `@Schedule` did. The ordering argument is untouched and if anything reinforced: the kernel holds route authorization at tier `preview` and moved it twice in one minor (ADR-077's `Execution` facet, then the composition work)
- [x] **Flow step identity (kernel ADR-062)** — resume now binds to a step's *name* rather than its position: `FlowDefinition` rejects duplicate step names, a parked snapshot records the name it stopped at, and a wake whose plan disagrees fails closed. `@SagaStep.name` has always been documented "unique within saga", so the surface needs no change — but the sentence stopped being a convention and became an enforced contract, and *renaming* a step is now a breaking change for in-flight sagas rather than a refactor. **Landed (0.10.0):** javadoc refreshed to say so, including the kernel's drain-before-reorder procedure. Deliberately **not** adding cross-step uniqueness validation to `SagaStepMetadata` — it is a per-step record and the constraint is a property of the list; the kernel validates it where definitions are built, which is the right place for a design-time carrier to defer to

## 0.12.0 — the SDK's own contract, made machine-readable

> Goal: stop being a repo whose contract can only be read by a human. Ship a
> generated catalog of the annotation surface, and re-check the two reserved
> facets against kernel 0.12.
>
> **Why this milestone exists.** 0.11.0 shipped and moved the one downstream ask
> that has never had upstream progress by exactly nothing. `exeris-ai-bridge`'s
> whole `sdk:*` family — five tools — reads a catalog that no artifact produces,
> so its 0.6.0 is blocked on this repo rather than on work in that one. Verified
> 2026-08-27 against the published artifacts rather than against the changelog:
> every 0.11.0 jar (`annotations`, `source-model`, `source-model-io`,
> `composition-spec`) carries class files plus `META-INF/maven` and nothing else,
> and the `v0.10.0` and `v0.11.0` GitHub Releases carry **zero assets** — so
> there is no channel by which a downstream `prepack` could vendor anything, and
> nothing on the other end of it. Released alongside kernel 0.12.

- [x] **`annotation-catalog.json`, generated upstream and attached to the
  release** — annotation names, `@Target`, `@Retention`, per-attribute
  name / type / default / required-ness, deprecation status with its canonical
  replacement, and the prose purpose of each. **The obvious mechanism is the
  wrong one**, and the downstream ask proposes it: "`AnnotationContractTest`
  already discovers every annotation by classpath reflection, so the emitter is
  that mechanism plus a serializer." Reflection recovers names, types, defaults,
  `@Target`, `@Retention` and `@Deprecated(forRemoval, since)` — and then stops
  short of the two things that make a catalog worth serving. **(a) The prose.**
  Not because the annotations are `@Retention(SOURCE)` — a class file carries no
  javadoc for anything at any retention, so the retention is a true fact standing
  next to the reason rather than being it. What is lost is each attribute's
  purpose text, which is most of what `sdk:describe_annotation` exists for, and
  the *canonical replacement* for a deprecation, which lives in `@deprecated`
  prose (`@Validation.required` → `@Field.required`) and not in the `@Deprecated`
  annotation, whose two elements are `forRemoval` and `since`. **(b) Nested
  declaration sites.** The package walk skips nested types and says so in its own
  comment. Counted from the 0.11.0 sources: **71 `@interface` declarations — 51
  top-level, 20 nested.** The 20 a reflection emitter would silently omit are
  ones authors actually write — `@DomainEvent.Header`, `@SagaStep.InputMapping` /
  `.OutputMapping` / `.CommandHeader` / `.MetricTag`, `@GraphEdge.PropertyMapping`
  / `.StaticProperty` / `.ComputedProperty`, `@Saga.SagaTrigger`,
  `@EventSourced.StreamMetadata`, `@Graph.GraphqlQuery` — and a catalog that is
  51/71 complete is worse than no catalog, because its consumer cannot tell which
  half it got. So the emitter reads the **declaration model plus doc comments**:
  a `jdk.javadoc.doclet` on an extra `maven-javadoc-plugin` execution, which is
  JDK-provided (no dependency added to the most upstream repo in the ecosystem)
  and whose `javax.lang.model` walk descends into nested types by construction.
  JavaParser is the alternative and is the wrong one twice over — ADR-037
  confines it to `-io`, and reaching for it here would have the annotations
  module parsed by a module that sits below it
- [x] **Distribution is the actual gate, and it does not wait for Central** —
  two channels: `META-INF/exeris/annotation-catalog.json` inside the annotations
  jar, so anyone who resolves the artifact has it; **and a GitHub Release
  asset**, which is what unblocks the downstream today because it needs no
  publishing infrastructure whatsoever. The SDK's Central move stays sequenced
  behind the kernel and `exeris-tooling`, and this deliverable must not inherit
  that gate — the zero-asset releases above are the whole of why the ask is still
  open. The catalog stamps the SDK version it was generated from, so a consumer
  pinning a different one can say so instead of answering from the wrong contract
- [x] **Non-vacuity: the catalog is gated, not merely emitted** — a guard
  asserting it covers every `@interface` the *source* declares, with the expected
  set derived rather than written down, verified against a deliberately added
  annotation. The 71 / 51 / 20 counts above are evidence for the design choice,
  not constants to hard-code — the drift between 0.10.0 (49 top-level) and
  0.11.0 (51) is precisely the argument the downstream makes for generating this
  upstream at all
- [x] **JSON Schema for the AST records** (`DomainMetadata` + siblings) — the
  second half of the same ask. `META-INF/exeris/ast-schema.json` ships inside
  `exeris-sdk-source-model` and is attached to the GitHub Release: 61 definitions
  (every record and enum in `…sourcemodel.ast`, nested ones included), draft
  2020-12, `$ref`-linked, rooted at `DomainMetadata`. Both Jackson constraints are
  **in the document**, not in a wiki page: `x-exeris-reader-requirements` states
  them, every primitive property is flagged `x-exeris-primitive` (the set on which
  an *explicit* null is fatal without the flag — an absent one binds the type
  default and is harmless, per the 2026-08-26 correction), and each definition and
  overriding property carries its
  `x-exeris-json-include` — so "is a zero meaningful here?" is answerable from the
  schema. Emitted by the same processor technique as the annotation catalog, so it
  needs no schema library and no second pass over the sources

### Landed — and what building it found

> The catalog is a `jdk.javadoc.doclet`-class problem solved with an annotation
> processor instead: `javax.lang.model` plus `com.sun.source.util.DocTrees` gives
> the declaration model *and* the parsed doc comments from inside the annotations
> module's own compilation, with no new dependency and no second pass over the
> sources. The doclet route in the bullet above would have worked; this one is
> smaller and runs where the build already is.

- [x] **Sixteen nested annotations were outside the contract this module states**
  — `@Retention` absent (so `CLASS` by default, not `SOURCE`) and `@Target` absent
  (so applicable anywhere). They now declare `@Retention(SOURCE)` and
  `@Target({})`, the empty target set that makes a type usable *only* as another
  annotation's member value — which is what they had always been by convention
  and never by declaration. Found because the catalog reports retention and
  targets per entry, and 16 of 71 came back null. `AnnotationContractTest` could
  not have caught it: its walk skipped nested types, with a comment giving the
  reason as "they inherit SOURCE retention at the use site" — true of the use
  sites that existed, and not a property of the declarations. The walk now
  descends, verified against a deliberately un-retained nested type
- [x] **Every declaration site carries prose** — 7 nested annotations and 26
  attributes had no javadoc at all, so a catalog entry for them would have been a
  name and a type. All of them nested, which is why nobody noticed: the surface a
  package walk sees was already documented. `AnnotationCatalogContractTest` fails
  on a missing `purpose` rather than shipping a blank one
- [x] **The SDK could not say a route is public — `@RouteAccess`, reserved** —
  the full account is in the corrected route-authorization item above. Three
  things are worth keeping here because they are the design, not the history.
  **Absence carries the third state.** There is no `UNSPECIFIED` constant on
  either side: an element with no `@RouteAccess` declared nothing, one that
  carries it decided, and the AST component is nullable to match. A sentinel
  would rebuild one level down exactly the "empty means two things" ambiguity the
  annotation exists to remove — which is also why `value()` is mandatory.
  **Scopes, not roles.** `RouteRequirement` declares no role kind at all, so
  `permissions` is the half of the existing surface that maps to a named scope
  and `@RouteAccess` supplies only the half it cannot express — whether identity
  is required at all. Two constants, not four; one fact, one carrier.
  **One refusal recorded for the transcription slice:** `PUBLIC` beside a
  non-empty `permissions` is contradictory rather than redundant — a permit-all
  route runs its handler with no principal bound, so the scope check can never be
  satisfied. `exeris-tooling` rejects it at build time; the javadoc states it so
  the pair is not written
- [x] **`@Action.roles` has no AST carrier at all** — found while scoping the
  above, and distinct from it. `ActionMetadata` carries `permissions` and **no
  `roles` component**, so the attribute is not merely declared-but-unextracted
  (the `@ExerisDomain` case): it is untransportable by construction. **Recorded,
  deliberately not fixed.** Adding a carrier no processor writes and no generator
  reads would ship an inert AST component — the exact shape ADR-054 removed when
  it deleted `ValidationMetadata`, and the honesty pass exists to prevent. It is
  also the *less* useful half: the kernel's edge decides on scopes, and ADR-063
  keeps `hasRole(...)` out of the edge DSL rather than inventing a `ROLE_x`→scope
  convention. A carrier is warranted when a consumer exists, not before
- [x] **The annotation-surface gate rejected a brand-new mandatory element** —
  `AnnotationSurfaceContractTest` read "new element, no default" as a break for
  every annotation, but the rule protects *existing* usages and a brand-new
  annotation has none (the baseline's own `@Action#name` / `#label` are
  required). The gate now treats a declaring type absent from the snapshot as
  new; such an element is still reported so it must be recorded before the next
  change to it is gated. Verified non-vacuous by adding an undefaulted `probe()`
  to `@Blob` — still caught, with the original message
- [x] **Jackson's annotations never reach a record component, and the schema was
  quietly saying so** — `@JsonInclude`'s `@Target` is
  `{ANNOTATION_TYPE, METHOD, FIELD, TYPE, PARAMETER}` and does **not** include
  `RECORD_COMPONENT`, so an annotation written on a record component is propagated
  to the derived members and `RecordComponentElement.getAnnotation` returns `null`.
  The first emitter asked the component directly and got nothing — which meant the
  schema reported `FieldMetadata.min` / `max` / `minLength` / `maxLength` as
  ordinary `NON_DEFAULT` properties, i.e. it described the boxed-zero bug those
  per-component `NON_NULL`s exist to prevent *as if it were still present*. Reading
  the accessor and the backing field as well recovers all four, and exactly four —
  zero false positives across the package. Guarded at both levels, and verified
  non-vacuous by restoring the naive lookup
- [x] **Property prose is unreachable from annotation processing, and the document
  says so rather than looking truncated** — a component can be documented with a
  comment written above it *inside the record header*. Javadoc-the-tool renders
  those; annotation processing cannot reach them. Four routes were measured and all
  return `null`: `Elements.getDocComment` on the component,
  `DocTrees.getDocCommentTree(Element)`, `DocTrees.getPath` on the component (so
  there is no path for the tree overload either), and a path built to the
  component's `VariableTree` member off the record's own resolvable path. The
  derived accessor and field carry no source position, so neither helps. `@param`
  on the record **does** resolve — proven by probe — and is the canonical Java form,
  but **no** record in the package used it, so property-level `description` was
  empty. The document carried `x-exeris-prose-coverage` with the counts and the
  reason, rather than shipping a schema that reads as truncated.
  **Closed in the same milestone:** the fifteen header comments were transcribed and
  the remaining 347 components written, so all 362 properties and all 61 definitions
  now carry prose. Two gates hold it there — `AstComponentProseConventionTest`
  refuses the header form, `AstSchemaContractTest` refuses a coverage drop — because
  documenting it once is not the same as keeping it documented, and the artifact this
  schema ships on will sit on Maven Central permanently

## 1.0.0 GA — frozen contract

> Goal: any 1.x release is binary- and source-compatible with 1.0.0.

- [x] **Public API surface review — done; 103 public top-level types across the six publishable modules, all of them contract.** The criterion as written ("everything not in `internal/` is contract") describes a partition that does not exist: **there is no `internal/` package anywhere in the repo**, and on inspection there should not be — every module here is a deliberate API surface (annotations, AST records, a parser/writer, a manifest schema, a lifecycle interface, a boot conductor), so there is no implementation detail to hide behind one. Recorded as an answer rather than left implied, and restated for consumers in `MIGRATION-0.x-to-1.0.md` §3.

  **What was checked, and came back clean** — each verified against the sources, not assumed: no third-party type appears in any public signature (JavaParser stays inside `-io` bodies; no `tools.jackson` databind type escapes `source-model` or `composition-runtime`), so a 1.0 consumer inherits no transitive compile dependency; every public class is `final`, so nothing is subclassable and no protected surface exists; no public non-final instance field anywhere; the static-only holders (`SchemaVersion`, `SourceDigest`, `CompositionBinding`, `CompositionStampAssertion`) all have private constructors; and the §1 removal list matches the code exactly — three `@Deprecated(forRemoval = true)` members in main sources, three entries.

- [~] Pre-freeze reconciliations from the 0.9.0 sweep. **`@ExerisDomain(name=…)` — done: dropped.** The reader read an attribute the annotation does not declare and whose javadoc claimed the processor used it; the processor takes `element.getSimpleName()` and has no override, so the reader could hand back a different identity than the processor for the same source (an ADR-042 parity break, not a cosmetic one).
