# Exeris SDK — Roadmap to 1.0.0 GA

The SDK defines the **contract** between user domain code and Exeris tooling.
1.0.0 GA means: **the contract surface is frozen**. Downstream consumers
(`exeris-tooling`, `exeris-platform-lsp`, IDE plugins, future capabilities)
can pin to it with semver guarantees.

This file tracks scope per milestone. Items marked `[ ]` are open; `[x]` shipped.

---

## 0.2.0 — quality gates + pre-publish hygiene

> Goal: CI exists, contract is testable, POMs are publishable.

- [x] **CI** — `.github/workflows/build.yml` runs `mvn -B -ntp verify` (Java tests + JaCoCo 85% instruction/line gate on source-model) and `npm run test:coverage` for the ui-kit (Vitest with v8 coverage, 85% per-file thresholds). JaCoCo + Vitest reports uploaded as artifacts on every run.
- [x] **JaCoCo 85% gate on `exeris-sdk-source-model`** — `jacoco-maven-plugin` 0.8.14 (earlier versions don't support JDK 26 class file v70); current measured coverage is 99.9% instructions / 100% lines / 94% branches across 50 classes. Annotations module is exempt from the gate (no executable code) but has `AnnotationContractTest` enforcing SOURCE retention + @Target across all top-level annotations via reflection — caught a real contract violation on first run (`SoftDeletedBy` was RUNTIME-retained, now fixed).
- [x] **JSON round-trip tests per AST record** — `AstJsonRoundTripTest` exercises every AST record (19 in total, including the three graph leaves directly) through Jackson 3 serialize → deserialize and asserts deep equality. Caught two real wire-format bugs on first run: (a) `ActionParamMetadata` was a class with record-style accessors that Jackson 3 didn't recognize as getters, dropping every field on serialization — fixed by migrating to a record (consistent with all other AST types); (b) Jackson 3 strict-mode rejects `null → primitive` coercion that Jackson 2 tolerated — `FAIL_ON_NULL_FOR_PRIMITIVES=false` requirement documented in `eu.exeris.sdk.sourcemodel.ast` package-info as a consumer contract. Known limitation: `@JsonInclude(NON_DEFAULT)` on `FieldMetadata` drops `Long(0)` because Jackson 3's NON_DEFAULT treats boxed-zero as "empty" — tracked under Field/Validation overlap fix
- [x] **Java 26 baseline rationale** in README (kernel ↔ Panama/VT requirement) — explains why 26 is required (kernel uses Virtual Threads + Panama FFM, processor must match consumer's `javac`), so teams on 21 LTS don't assume the baseline is an oversight
- [x] **Field/Validation overlap fix** — picked canonical locations: `required` lives on `@Field` (it's a field-shape property, not a validation rule); `inCreate`/`inUpdate` stay on `@Field` (form-lifecycle scope). `@Validation.required` and `@Validation.validateOn` are now `@Deprecated(forRemoval = true)` with javadoc pointing at the canonical attributes — to be dropped in 1.0.0. Documented end-to-end in `eu.exeris.sdk.annotation` and `eu.exeris.sdk.sourcemodel.ast` package-info. Wider `min`/`max`/`pattern` overlap between `FieldMetadata` and `ValidationMetadata` is documented and deferred to the 0.6–0.9 cleanup phase, where budgetHQ usage will inform the right cut (landed 0.9.0 — ADR-054)
- [x] **Pre-publish POM metadata** — root POM now declares `<url>`, `<organization>`, `<licenses>`, `<developers>`, `<scm>`, `<issueManagement>`, `<distributionManagement>` (Sonatype Central Portal). Required by Maven Central; without these the publish step would fail validation
- [x] **Bump `jackson-annotations` `3.0-rc5` → `2.21`** — Jackson 3.x deliberately keeps annotations on the legacy 2.x line (per jackson-bom 3.x: `jackson.version.annotations=2.20+`). The 3.0-rc* annotations track was abandoned. Required for Jackson 3 databind 3.1.2 to load (`JsonSerializeAs` is a 2.21 addition)

## 0.5.0 — bidirectional sync surface

> Goal: SDK exposes the metadata mutations that LSP, Studio, and IDE plugins call. Design locked in [ADR-042](docs/adr/ADR-042-bidirectional-mutation-surface.md) (implements [RFC-2026-06-11](docs/rfc/RFC-2026-06-11-source-model-conflict-resolution.md)); records in `source-model`, detection + application in `-io`, baseline-trust fields emitted by `exeris-tooling` codegen.

- [x] `MutationOp` records (add/rename/change-type field, change relationship cardinality, …) — `source-model`, path-addressed (ADR-042 slice 1). Sealed interface with nine nested op records (`AddField`/`RemoveField`/`RenameField`/`ChangeFieldType`/`AddRelationship`/`RemoveRelationship`/`ChangeRelationshipCardinality`/`AddAction`/`RemoveAction`); polymorphic JSON via an `"op"` discriminator. New package `eu.exeris.sdk.sourcemodel.mutation` (operations over the AST, not AST nodes); JavaParser-free, Jackson-only — zero-coupling enforcer green
- [x] `MutationResult` records — four outcomes: `SUCCESS` / `CONFLICT` / `VALIDATION_ERROR` / `NO_BASELINE` (ADR-042 slice 1). Sealed interface; `Conflict` carries baseline/current/intended values; `NoBaseline` shape frozen with a `NoBaselineCause` enum (`MISSING_BASELINE`/`STALE_DIGEST`/`SCHEMA_VERSION_SKEW`); `"outcome"` discriminator
- [x] Path-based addressing (`/entities/Order/fields/total`) — shared by ops and conflict reports. `MutationPath` (build/parse/validate + `isSameOrAncestorOf` for the slice-2 ancestor-or-descendant rule); ops carry the path as a plain wire string
- [x] AST-level three-way conflict detection in `-io` (ancestor-or-descendant overlap; convergent edits are `SUCCESS`) — ADR-042 slice 2. `SourceModelConflictDetector.detect(op, baseline, current)` compares `read(currentSource)` against the deserialized baseline at member granularity (field/relationship/action paths): drift = current ≠ baseline; conflict = drift ∧ non-convergent (the user hasn't already landed on the op's intent); sibling edits never conflict. Returns `SUCCESS`/`CONFLICT`, plus `VALIDATION_ERROR` for the structural rejections visible without a baseline (unparseable path, path-kind/op mismatch, wrong entity). Pure over two `DomainMetadata` values — no source reading, no digest, no `NO_BASELINE` (slice 3) and no mutation (slice 4). Hand-built SUCCESS/CONFLICT/convergent/sibling matrix + a budgetHQ corpus-backed case
- [~] Baseline-trust fields (ADR-042 slice 3, **cross-repo**). **SDK side done:** `source-model` gains the shared contract — `SchemaVersion.CURRENT` (a dedicated wire-format-schema constant, decoupled from the Maven artifact version so a no-AST-change release doesn't read as a skew), `SourceDigest` (pure, JavaParser-free, line-ending/trailing-whitespace-neutral SHA-256 so both codegen and `-io` compute it identically), and `BaselineTrust` (the two trust fields as JSON siblings of the domain, each read blind to the other via `ignoreUnknown`). `-io` `SourceModelConflictDetector.checkBaselineTrust` + JSON/source `detect` overloads map missing/unparseable/schema-skew → `NO_BASELINE` before detection. **Decision:** per ADR obligation 4–5 tension, `STALE_DIGEST` is **not** a detection-time block — three-way detection runs on an edited source (its whole point); the digest is the apply-time optimistic-concurrency token (slice 4). **Remaining (cross-repo):** `exeris-tooling` codegen emits `sourceDigest` + `schemaVersion` into each `exeris-metadata/<entity>.json` + the `.link.md` stub
- [x] Conflict-aware application + optimistic concurrency token (ADR-042 slice 4). `SourceModelMutationApplier.apply(op, baselineJson, currentSource[, token])` composes detection (slices 2–3) with the idempotent writer: applies only on a `SUCCESS` verdict — never over a non-convergent user edit — and returns `ApplyResult{outcome, source}` (source returned unchanged on `CONFLICT`/`NO_BASELINE`/`VALIDATION_ERROR`; idempotent no-op when the op is convergent). The `sourceDigest` is the apply-time optimistic-concurrency token → `STALE_DIGEST` when the live source moved since the op was computed. `VALIDATION_ERROR` covers `changeRelationshipCardinality` (structural — no writer mutation behind it) and writer/parse rejections. Single-op; conflict-aware **batch** apply is deferred (it must thread the accumulating tooling edits through detection — own semantics)

### Annotation-surface honesty — inert attributes (issues to address)

> An internal surface review found attributes the SDK **advertises** but no consumer honours — they read as live configuration while silently doing nothing. Logged here as roadmap issues (not yet opened on GitHub). The SDK-owned obligation is the same in every case — **make the annotation tell the truth**: wire it end-to-end, or run the deprecation pipeline so it stops reading as configuration. Some pair with a downstream gap (a tooling consumer or a kernel SPI) tracked in `exeris-tooling` / `exeris-kernel`.

- [x] **`@ExerisDomain` system-field overrides are inert** — all nine override attributes (`tenantIdField`, `versionField`, `softDeleteField`, `softDeleteTimestampField`, `softDeletedByField`, `createdAtField`, `createdByField`, `updatedAtField`, `updatedByField`) are advertised, but the repository generator hard-codes the canonical accessor names. Decide: honour them in tooling, or deprecate + document the canonical names (`tenantId`/`version`/`createdAt`/`createdBy`/`updatedAt`/`updatedBy`/…) as mandatory in `MIGRATION.md`. **Resolved (honoured in tooling, T5/T6):** the processor extracts the overrides into `SystemFieldsMetadata` and the repository + Flyway generators resolve each logical field through it (`KernelRepositoryGenerator`, `KernelFlywayGenerator`), falling back to the canonical accessor only when an override is unset — the attributes are live, not inert.
- [x] **`@Relationship.targetEntity` is inert** — the processor derives the target from the field's Java type, so the attribute does nothing on the explicit-UUID-FK style. Decide: document the entity-typed requirement, or push tooling to prefer `targetEntity` when set (fall back to the field type only when `void.class`). **Resolved (honoured in tooling, T4):** the processor now prefers `targetEntity` when set and falls back to the field type only when unset.
- [x] **`@Action(name=…)` is inert** — action identity is the method name, so a `name` chosen to dodge a bean-setter collision has no effect, even though `name` is a *required* attribute. Decide: clarify in the javadoc that the method name is the identity today, or make tooling honour `name` as the stable action id. **Resolved (honoured in tooling, T3):** the processor reads `name` as the action identity and it flows through to the emitted action path/id.
- [x] **`@DomainEvent.topic` is inert against the Open-Core event bus** — topic routing is an enterprise/Kafka-tier concern. Javadoc note that `topic` is enterprise-tier routing metadata, ignored by the Open-Core event engine. **Resolved (javadoc-honesty):** `@DomainEvent.topic` carried an Open-Core-status note — the Open-Core event engine does not route on it (the generator preserves it as a source reference only); it gains meaning under the enterprise/Kafka messaging tier. **Superseded (kernel v0.10.0, ADR-050 — see `docs/adr/ADR-050.link.md`):** `topic` now has a binding-agnostic kernel sink — an optional `EventTypeSpec.topic` on the per-*type* registration record (blank ⇒ "no override"), honoured by the **Community Kafka binding on both publish and subscribe** (`effectiveTopic` = override, else type name; `topicPrefix` still applies) — so topic routing is live in Open-Core under a broker binding, no longer enterprise-tier-only; the in-memory `EventBus` stays topic-blind by design (ADR-049 H2). The `@DomainEvent.topic` javadoc stance is updated to match — the SDK's ADR-050 lockstep obligation, done. **Tooling lockstep landed too (exeris-tooling #132, verified on main 2026-07-02):** the `KernelEventGenerator` now populates `EventTypeSpec.ofPersistent(name, ordinal, topic)` from the declared topic (blank ⇒ 2-arg factory, "no override") — the `@DomainEvent.topic` → AST → generator → `EventTypeSpec` → Kafka `effectiveTopic` chain is live end-to-end; the in-memory bus keeps it advisory.
- [x] **Capability surface is inert end-to-end** — `@Provides` / `@Requires` / `@CapabilityModule` (+ their AST records) are read into the AST (0.4.0 Slice 3) but no processor extraction nor codegen consumer uses them. Decide: wire the graph end-to-end with a tooling registry consumer, or a javadoc + `MIGRATION.md` note that the capability annotations are reserved and not yet consumed in Open-Core. **Resolved (SDK side — javadoc-honesty):** the `capability` package-info now carries an "Open-Core status — reserved, not yet consumed" note (declared shape + `-io` reader exist, but no processor extraction / codegen consumer yet, so declaring them has no generated effect). Wiring the cap graph end-to-end remains `exeris-tooling` work. **Superseded (0.8.0/0.9.0 — consumed end-to-end):** the tooling processor extracts the capability annotations, `VerifyCapabilitiesMojo` + `CapabilityGraph` validate the dependency DAG, the stamped `cap-manifest.json` is emitted, and the 0.9.0 boot conductor drives the four-phase lifecycle from it — the capability package-info now carries the live "extracted and conducted" status. The remaining not-yet piece is the tooling-generated SKU bootstrap call site (gateway-caps plan).
- [~] **Streaming / real-time attributes are inert** — `@ExerisDomain(realTimeApi=true)` and `@Action(streaming=true, streamEventType=…, realTimeUpdates=true)` advertise server-push, but there is no Open-Core streaming HTTP SPI to back them (kernel-owned root cause). Javadoc note that they are not wired in Open-Core until the kernel streaming affordance lands; the annotations gain meaning once it does. **Resolved (javadoc-honesty):** all four attributes (`@ExerisDomain.realTimeApi`, `@Action.streaming` / `streamEventType` / `realTimeUpdates`) carry an Open-Core-status note that they are inert until the kernel streaming HTTP affordance lands. **Unblocked (kernel v0.10.0 — shipped 2026-07-02; ADR-043 ACCEPTED 2026-06-21):** the kernel streaming HTTP SPI (`HttpStreamHandler` / `HttpStreamExchange` / `StreamEvent` / `HttpRouter.streamRoute`) landed, so the SDK → tooling streaming chain is unblocked; the emitter shape is fixed in [RFC-2026-06-22 (tooling)](https://github.com/exeris-systems/exeris-tooling/blob/main/docs/rfc/RFC-2026-06-22%20SSE%20Stream%20Emitter%20%28tooling%29.md) — see `docs/adr/ADR-043.link.md`. The entity-level driver (`DomainMetadata.realTimeApi`) was already plumbed (tooling Slice 1, unblocked today). **SDK side done (0.8.0):** the per-action driver's AST gap is closed — `ActionMetadata` grew `streaming` / `streamEventType` / `realTimeUpdates` (additive, by-name, blank `streamEventType` → null, schema bumped to `0.8.0`), the faithful AST twin of the `@Action` attributes, with round-trip + focused-test coverage. **Tooling landed (verified 2026-07-02):** the processor extracts `@Action(streaming)` and the emitters shipped (tooling Slice 1 #104 + Slice 2 #106) — the **entity-level** chain is live end-to-end with a real `@DomainEvent`-bus feed (tooling #125); the **per-action** stream body is still a keep-alive scaffold pending the tooling **EV1-stream** producer pass. **Javadoc stance refreshed (2026-07-02):** the attribute notes now carry the kernel-v0.10.0 status — `realTimeApi` live at the entity level, `streaming`/`streamEventType` partially live pending EV1-stream, `realTimeUpdates` still inert (deliberately unextracted tooling-side until it has a generator consumer). **Parity closed (SDK 0.8.0):** the `-io` reader now extracts the per-action streaming driver (`streaming` / `streamEventType`) in processor parity; `realTimeUpdates` stays unextracted on both sides (deliberate — no generator consumer yet). **Remaining (cross-repo):** the tooling **EV1-stream** producer pass (the per-action real feed behind the emitted route).
- [ ] **No `universe` data-scope tier** — the surface offers only global-singleton and tenant-private (`tenantScoped`), so a dataset that many tenants co-inhabit and read across (rather than each tenant's private rows) is unmodellable and `tenantScoped` does double duty; needs a third kernel RLS mode. Add a first-class universe scope to `@ExerisDomain` (cross-tenant-readable, row-owned but not row-hidden) once kernel persistence supports it. **Direction set (SDK side) in [RFC-2026-06-24](docs/rfc/RFC-2026-06-24-universe-data-scope-expression.md) (ACCEPTED 2026-07-02):** the recommended shape is an AST-owned `DataScope { GLOBAL, TENANT, UNIVERSE }` discriminator replacing the `tenantScoped` boolean's intent (deprecation fallback `true→TENANT`/`false→GLOBAL`), with `UNIVERSE` shipped reserved (streaming-style honesty note) until kernel enforcement is live; the SDK encodes author intent only, never the `StorageContext` carrier. **Kernel decision landed (kernel v0.10.0, decision-only — [RFC-2026-07-02](https://github.com/exeris-systems/exeris-kernel/blob/main/docs/rfc/RFC-2026-07-02-shared-scope-isolation-tier.md) ACCEPTED 2026-07-02):** the shared tier is an **orthogonal row-visibility dimension** — `sharedScopeKey` + a `SHARED_WORLD` visibility mode composing with the physical `IsolationStrategy`, not a fourth strategy value; kernel-neutral naming ("Universe" stays the SDK-facing name, tooling records the mapping); write model = read-widen + owner-scoped write. The kernel ruled the two layers consistent — *mutually exclusive at expression, orthogonal at the physical layer* — so **the three-way `DataScope` enum holds** and RFC-2026-06-24 moved off DRAFT (build trigger (1) met). **Build still gated (upstream):** trigger (2) — the ADR-012 in-place amendment (carrier sub-shape + a shared-scope claim — name TBD, `SHARED_SCOPE_KEY` favoured — + cross-tenant-readable RLS mode with TCK on the read-widen and write-pin paths) — has not landed; when it does, `UNIVERSE` ships reserved with the streaming-style honesty note until enforcement is live. Pairs with the `ProjectionMetadata` public-vs-private-state item below.

- [~] **Unified presentation / front model (`@View` / `ViewMetadata`)** — the legacy presentation surface is entity-attached (`@UI` / `@UIGroup` / `@Tab` / `@NavMenu` / `@Field.ui`), so every generated view derives from one `@ExerisDomain`; a page composed from many content types, an authored-only section, or a fully backend-less front is unmodellable — the gap a Headless CMS needs. **Accepted in [RFC-2026-06-25](docs/rfc/RFC-2026-06-25-presentation-front-model.md):** a framework-neutral presentation IR (`@View` / `ViewMetadata` tree: view→region→component→binding) riding the existing metadata-JSON; SDK owns the IR (front facet), the **Angular 22 signal-first emitter is `exeris-tooling`**, ui-kit stays framework-agnostic. Binding = `source` discriminator (`ENTITY` / `PROJECTION` / `ACTION` / `STATIC` / `SLOT` / `NONE`) + opaque ref/path/expression. Extends ADR-003: entity = SoT for *data*, the IR = SoT for *composition* (orthogonal facets — entity-driven · composition · front-only · API-only). **This is one model, not a split: `@UI` is being *subsumed* by `@View`/`ViewMetadata`** (entity-level view selection → `@View`; field-level render detail → the leaf field facet of `ViewMetadata`, reusing `UIMetadata.UIFieldMetadata`) — an extension, not a parallel surface. **SDK seed shipped (reserved, 0.8.0):** `@View` / `@Region` / `@Block` / `@Bind` + `ViewMetadata` / `RegionMetadata` / `ComponentNodeMetadata` / `BindingMetadata` (+ `ViewKind` / `BlockType` / `BindSource`), with reserved-honesty notes; `-io` in parity (ADR-042). **Structural generation LANDED (reclassified consumed, 0.9.0 sweep):** the `exeris-tooling` processor extracts `@View` / `@Region` / `@Block` / `@Bind` into the IR and the codegen-ts view generator emits Angular components (RFC-2026-06-28, tooling); the SDK javadoc "reserved / no generated effect" notes are refreshed to the live status (this PR). **NOT yet implemented — the ADR-047 leaf-field facet** (`ViewFieldMetadata`, the `@UI` field-level subsumption): the facet exists only in the ADR document, and the processor constructs `ComponentNodeMetadata` with a null leaf-field facet — so `@View` cannot yet replace `@UI`'s field-level render detail. `@UI` therefore stays **undeprecated** through 0.9.0 (its own gate: deprecate only once `@View` can actually replace it); with 1.x minors additive-only, `@UI` is frozen through the 1.x line. Plan of record: the ADR-047 facet lands in tooling during 1.x → `@UI` gains `@Deprecated(forRemoval)` in that 1.x minor (deprecation is additive metadata, legal in a minor) → removal at 2.0. **Umbrella (platform-scope, `exeris-docs`):** the [publishable-unit / marketplace RFC](https://github.com/exeris-systems/exeris-docs/blob/main/rfc/RFC-2026-06-25-publishable-unit-marketplace.md) (DRAFT); the SDK's only net-new slice there is a thin optional `@Listing` catalog facet.
- [ ] **System/security field-marker annotations + `@ExerisDomain.validationMode` are declared-but-unconsumed** — the ten `eu.exeris.sdk.annotation.system` markers (`@TenantId`, `@PrimaryKey`, `@Version`, `@SoftDelete`, `@SoftDeletedBy`, `@SoftDeleteTimestamp`, `@AuditCreatedAt`/`By`, `@AuditUpdatedAt`/`By`) and the two `security` markers (`@Encrypted`, `@RowLevelSecurity`) read as functional, but the tooling processor never scans fields for them; the **live** system-field path is the `@ExerisDomain` field-name override attributes (honoured in tooling, T5/T6) falling back to the canonical accessor names. `@ExerisDomain.validationMode` claims to govern marker-validation strictness, so with no marker scanning it is inert *by construction*. Javadoc honesty notes added (system package-info created; security package-info + the `validationMode` attribute carry reserved notes — this PR); the markers stay reserved until processor field-scanning lands. Wiring-or-deprecation decision deferred to the 1.0.0 public-API surface review.
- [ ] **`@Relationship.relationshipType` is never extracted** — tooling-side latent bug: the processor reads annotation key `"type"` but the annotation declares `relationshipType()`, so the declared cardinality enum never reaches the AST. Fix belongs to `exeris-tooling` (scheduled for the post-0.9.0 SDK pin bump); no SDK surface change.

### UI kit — gaps to address

> The same surface review exercised `exeris-sdk-ui-kit` against a generated app and found gaps between what the kit ships and what generated UI needs. These connect to the broader ui-kit scope question (the kit is today a Tailwind preset + a handful of component classes). Tooling-side items (codegen-ts emitter parity) are tracked in `exeris-tooling`. Suggested order: **B1+B2 → B5 → B3 → B4**.

- [x] **B1 — Tailwind major mismatch (headline).** Resolution: **ship a v4 `@theme` entry alongside the v3 JS preset** (the additive, non-breaking option — not a forced major sync). `exeris-sdk-ui-kit/src/styles/theme.css` declares the same `exeris-*` token namespace via `@theme`, so a v4 consumer (`@import "tailwindcss"; @import "@exeris/ui-kit/theme";`) gets the same `bg-exeris-primary`/`font-exeris`/`rounded-exeris-md`/`shadow-exeris-lg`/`animate-exeris-*` utilities the v3 preset gives. A parity test (`tests/theme.test.js`) pins v4 @theme ↔ v3 preset ↔ raw `index.css` channels (incl. `transitionDuration`) so they can't drift. (A future single-major unification across the ecosystem stays open, but the v4 blocker is cleared.) **Follow-up:** the parity guard is text-level — `theme.css` is not yet compiled through a real Tailwind v4 toolchain in CI (the kit's single `tailwindcss` devDep is v3, and v3's `index.css` `@tailwind` directives can't share it), so v4-namespace correctness isn't compiler-validated yet.
- [x] **B2 — preset not in package `exports`.** `package.json` `exports` now maps `./tailwind.preset.js` (so the README's `import … from '@exeris/ui-kit/tailwind.preset.js'` resolves under `exports` enforcement) and `./theme` (the B1 v4 entry). README documents both the v3 and v4 wiring.
- [x] **B5 — `@Field.dataType` lost at the annotation→AST boundary.** **SDK side done:** `FieldMetadata` now carries a `dataType` component (builder + accessor + `AstJsonRoundTripTest`/`FieldMetadataTest` coverage; additive wire-format change, by-name JSON so back-compatible). The `dataType` vs `format` split is documented in the `ast` package-info: `dataType` = the *semantic* kind from `@Field.dataType` (`currency`/`percent`/`url`), `format` = an explicit *presentation* format string (no `@Field` source today). **Deliberately NOT populated yet** to preserve the reader↔processor parity conflict detection relies on (ADR-042): wiring the `-io` reader to read `@Field.dataType` while the build-time processor does not would diverge from the codegen baseline. **Closed (0.8.0):** the coordinated flip landed — the `exeris-tooling` processor and the `-io` reader now extract `@Field.dataType` together (the reader wired in the EV1 PR #74; unset stays null, nothing leaks onto the wire), restoring populated reader↔processor parity.
- [x] **B3 — component styles cover the full `ComponentType` set.** Added styled `.exeris-*` classes for every renderable `ComponentType` (27 kinds) beyond the text inputs `.exeris-input` already covered: `.exeris-select` (SELECT/MULTI_SELECT), `.exeris-textarea`, `.exeris-checkbox`, `.exeris-radio` (+ `.exeris-radio-group`), `.exeris-toggle` (CSS switch), `.exeris-range` (SLIDER), `.exeris-file` (FILE/IMAGE upload), `.exeris-color`, `.exeris-editor` (RICH_TEXT/CODE), `.exeris-rating`, `.exeris-chips`/`.exeris-chip`. `AUTO` is codegen-resolved, `HIDDEN` renders nothing. Also fixed a pre-existing stray-`c` char at EOF that had been silently breaking `npm run build:css` (CI only runs `test:coverage`). Classes live in the v3 `index.css` component layer; v4-consumer component-class parity is a separate follow-up (B1 shipped v4 tokens, not components).

When non-empty the key resolves against the app bundle with the literal as fallback; empty ⇒ literal verbatim. Builder normalizes blank ⇒ null (NON_DEFAULT). ### AST expressiveness — behaviour, choreography, topology (modeling gaps)

> Exercising the SDK against a non-trivial generated domain (well beyond the CRUD-shaped corpus) surfaced a class of gaps distinct from the inert-attribute fixes above. The AST models **structure** richly — entities, fields, actions, events, and sagas-as-an-ordered-list — but models **behaviour** (what a step or handler *does*), **choreography** (which event drives which reaction), and **topology** (which service exposes what) thinly. The consequence is that a generated app's *scaffolds* are real but their *bodies* are hand-written, because the AST can't describe what a design-time tool (LSP / Studio) would draw. The SDK-owned obligation here is the same in each case: **grow the AST/annotation surface to express it**; the matching generation is `exeris-tooling`. The topology half is partly already covered — the capability annotations (0.4.0) carry the provide/require graph — so what remains SDK-side below is mostly behaviour + choreography. RFC-worthy in aggregate (each is a sizeable additive surface); list-only for now, no GitHub issues yet.

- [~] **Saga step semantics + typed transitions.** `SagaStepMetadata` is already a rich step descriptor — `order`, `service`/`command`, `compensation`, `timeout`/`maxRetries`/`retryBackoff`, `parallel`, `required`, `condition`/`skipOnConditionFalse`, `dependsOn` (a partial DAG), `producesEvents`, `inputMapping`/`outputMapping`, `errorHandler`. Two things are still missing: a step *kind* (await-timer / await-event / invoke / compensate — today the kind is only implied by which of `service`/`command`/`compensation` is set) and **typed transitions** as first-class edges (success → next, failure → compensate, timeout → retry; loops). `dependsOn` orders steps but doesn't carry the *outcome* an edge fires on, so a branch the consumer must encode by hand (via the returned outcome) can't be drawn or generated. Model step `kind` + a typed-transition shape (`@SagaTransition(from, to, on = SUCCESS | FAILURE | TIMEOUT)` or equivalent) so the await/dispatch/compensate body becomes generable; emission is tooling. Promotes the step list + `dependsOn` DAG into an outcome-edged state-machine graph. **SDK side done (0.7.0):** `SagaStepMetadata` grew `kind` (`StepKind` = INVOKE / COMPENSATE / AWAIT_EVENT / AWAIT_TIMER) + `effectiveKind()` (infers INVOKE/COMPENSATE from structure; await kinds need the explicit field), and `SagaMetadata` grew `transitions` (a `SagaTransition` edge list = `from` → `to` `on` a `TransitionOutcome` of SUCCESS/FAILURE/TIMEOUT/COMPENSATED, optional SpEL `guard`, null/blank `to` = terminal), with `hasTransitions`, factories (`success`/`failure`/`timeout`/`ofOutcome`), compact-constructor normalization (null-list → empty, default outcome SUCCESS, blank guard → null, blank `to` → null, `from` required non-blank) and defensive copy. Round-trip + focused-test coverage added; AST-owned enums (no annotation mirror, zero-coupling); schema stays `0.7.0` (same release as the ProjectionMetadata growth). **Annotation half done (0.9.0, shipped reserved):** `@SagaTransition` / `@SagaTransitions` (repeatable, saga-class-level: `from`/`to`/`on`/SpEL `guard`, blank `to` = terminal edge) + `@SagaStep.kind` (`UNSPECIFIED` default = absent AST kind, deferring to `effectiveKind()` inference), with annotation-side `TransitionOutcome`/`StepKind` enum mirrors of the AST-owned types (zero-coupling, the `ComponentType` precedent) and `@Derived`-style reserved-honesty notes. **Remaining (cross-repo, coordinated):** the `exeris-tooling` processor extraction into the grown record, with the `-io` reader extracting them in parity; a codegen consumer then turns the graph into the await/dispatch/compensate body. The operational `@SagaStep` surface (circuit breaker, idempotency, instance selection, per-step monitoring) stays deferred (additive).
- [~] **Event reactions / choreography — the missing AST record.** The `@EventHandler` annotation already exists (`@Retention(SOURCE)`, `@Target({METHOD, TYPE})`, with event-selection, `condition`, `priority`/`ordering`, transaction/retry, and saga-trigger attributes), but there was **no `EventHandlerMetadata` AST record** — so the processor could read a `@EventHandler` and had nowhere to put it, and the AST/codegen never saw the choreography backbone. `@DomainEvent` models the *emission* side; the *reaction* side was invisible to the AST. **SDK side done:** `EventHandlerMetadata` added (record + builder + `simple` factory + `isSagaHandler`/`hasCondition` convenience; blank→null / null-list→empty normalization in the compact constructor), wired into `DomainMetadata.eventHandlers` (additive, by-name JSON; old baselines read back an empty list), with `AstJsonRoundTripTest` (projection + saga shapes) and a focused `EventHandlerMetadataTest`. It captures the behaviourally meaningful facets; the operational attributes (`emitMetrics`/`logLevel`/`alertOnFailure`), nested `@RetryPolicy`, and `versions` are deliberately deferred (additive). Enum-valued attributes are stored as source-written strings (zero-coupling, as the capability records do). **Remaining (cross-repo, coordinated):** the `exeris-tooling` processor extracts `@EventHandler` into the record and a codegen consumer turns it into the reaction (emit-command | mutate | invoke), with the `-io` reader extracting it in parity. Related and still open: `@DomainEvent(trigger = STATE_TRANSITION, stateTransition = …)` is declarative-only — the AST names "fire when field X changes" but nothing models the old/new diff end-to-end (detection emission is tooling).
- [~] **`@Projection` AST record is too thin.** Both `@Projection` (a full annotation — event subscription, read-model config, partitioning, rebuild/consistency, caching, REST/GraphQL exposure) and `ProjectionMetadata` (wired into `DomainMetadata.projections`) already exist — but the AST record carries only `name` / `description` / `fields` / `cacheable`. It has **no source-aggregate link and no field-subset framing**, so the "expose this subset of *this* aggregate as a read-only view" pattern — the public-projection-vs-private-state split that pairs with the `universe` data-scope item above — can't be expressed even though the annotation can. SDK obligation: grow `ProjectionMetadata` (source aggregate + exposed-field framing, bridging the annotation's event-subscription model), not add a new annotation; generating the DTO + mapping is tooling. **SDK side done (0.7.0):** `ProjectionMetadata` grew the source linkage (`aggregateTypes`), event subscription (`events` / `eventClassNames` / `topicPattern`), and read-model identity (`model` / `schema`) alongside the existing `fields` subset; added `builder` + `of(name, aggregateType, fields)` factory + `hasSourceAggregate` / `hasFields`, with blank→null / null-list→empty normalization, `AstJsonRoundTripTest` (full + minimal shapes) and a focused `ProjectionMetadataTest`. Class-valued attributes stored as source-written strings (zero-coupling). The operational surface (partitioning / rebuild / consistency / monitoring / query API) is deferred (additive). **Remaining (cross-repo, coordinated):** the `exeris-tooling` processor extracts `@Projection` into the grown record and a codegen consumer emits the read-model DTO + mapping, with the `-io` reader extracting it in parity.
- [~] **Declarative-behaviour layer (`@Derived` / `@Rule`).** The deepest pattern behind the above: the SDK models structure, so the pipeline emits scaffolds and *all* behaviour is hand-written code the AST never sees. A slice of that behaviour is mechanical — derived fields, roll-ups, simple guards/formulas — and could be modeled declaratively (`@Derived(expression = …)`, `@Rule(…)`) rather than written by hand, leaving genuinely-complex domain logic as a marked escape hatch (a design-time tool must always keep one). RFC-worthy (large new surface); informed by ready Capabilities + SKU workloads — the same "let real usage inform the cut" discipline as the Field/Validation overlap, not budgetHQ. Server-side `@Validation` generation and full `@UI` fidelity are the smaller, known instances of the same "modelled but not generated" gap (their SDK halves already exist; the generation is tooling). **Direction set in [RFC-2026-06-18](docs/rfc/RFC-2026-06-18-declarative-behaviour-layer.md) (ACCEPTED):** the framed surface (opaque-`String` expression + `language` tag defaulting to `"spel"`; opt-in escape hatch; `@Derived` as a `FieldMetadata` facet, `@Rule` + top-level `@Rules` container as a `DomainMetadata.rules` list; `dependsOn` allows related-entity paths). The build trigger is **met** — an internal adopter exercising the SDK against a non-trivial generated domain has a concrete recurring need (roll-ups incl. cross-aggregate, discriminant→value maps, ratio/threshold guards, decay formulas). **SDK side done:** `@Derived` / `@Rule` / `@Rules` annotations in `exeris-sdk-annotations` (slice 1) + `DerivedMetadata` / `RuleMetadata` AST records (slice 2 — `FieldMetadata.derived` facet + `DomainMetadata.rules` list, `effectiveLanguage`/`effectiveSeverity` defaults, blank→null normalization, round-trip + focused tests), shipped reserved with a capability-style "generation pending tooling" honesty note; shares the `"0.7.0"` schema. **Remaining (cross-repo, coordinated):** the `exeris-tooling` processor extracts `@Derived` / `@Rule` into the records and a codegen consumer emits the derivation / constraint, with the `-io` reader extracting them in parity. A reaction/choreography sibling (`@Reaction`-shaped) is out of scope (overlaps `EventHandlerMetadata` + the `STATE_TRANSITION` gap).
